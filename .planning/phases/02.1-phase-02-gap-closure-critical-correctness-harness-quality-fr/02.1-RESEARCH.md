## Finding-by-Finding Investigation

### CR-02: `Network::cast` — OUT param width mismatch

**File:** `UtinniCore/swg/misc/network.cpp:36, 65-71`

**Current state (verified by direct read):**

```cpp
// utinni.h:36
using swgptr = uint32_t;   // [VERIFIED: codebase read]

// network.cpp:36
using pCast = int64_t(__thiscall*)(swgptr*, int, int);
// ^^^                              ^^^ 4-byte slot

// network.cpp:65-71
int64_t Network::cast(int id)
{
    swgptr networkId = 0;               // 4-byte stack slot
    swg::network::cast(&networkId, id, (id >> 32));
    return networkId;
}
```

**The problem:** `pCast` declares the OUT param as `swgptr*` (pointer to a 4-byte slot). If `swg::network::cast` at RVA `0xAA4900` writes an 8-byte NetworkId through that pointer, it stomps 4 bytes of adjacent stack. [VERIFIED: codebase read]

**ABI investigation:**

The SWG RVA `0xAA4900` is not directly disassemble-able in this research session without the live binary. However the codebase contains two strong clues:

1. The comment on `pCachedNetworkIdGetObject` (network.cpp:34) reads `"pThis = CachedNetworkId, should be 8 bytes?"` — indicating the author expected 64-bit NetworkIds in this area of SWG. [VERIFIED: codebase read]
2. `Network::getObjectById` accepts `const int64_t& id` (network.h:36) — confirming that the NetworkIdManager API treats IDs as 64-bit on the lookups side. If the cast operation produces a value that `getObjectById` consumes, it must be 64-bit. [VERIFIED: codebase read]
3. The return type of `pCast` is already declared as `int64_t` — the person who wrote this typedef expected 64-bit output. The mismatch is that the OUT param was left as 4-byte.

**Disposition (D-06 option c — hybrid):**

Because disassembly is unavailable, apply the **default option (c) hybrid** per CONTEXT.md D-06:

```cpp
// Fix: widen OUT param to int64_t* while keeping int64_t return (harmless if SWG is 32-bit,
// correct if SWG is 64-bit). Also drop the UB shift (CR-03 fix).
using pCast = int64_t(__thiscall*)(int64_t*, int, int);

int64_t Network::cast(int64_t id)
{
    int64_t networkId = 0;
    swg::network::cast(&networkId, (int)(id & 0xFFFFFFFF), (int)((id >> 32) & 0xFFFFFFFF));
    return networkId;
}
```

This is safe regardless of SWG's actual behavior:
- If SWG writes 8 bytes through the ptr: now it has a correctly-sized 8-byte target. No stack stomp.
- If SWG writes only 4 bytes: `networkId` receives those 4 bytes and the high 4 remain zero. No regression.
- The parameter type widening from `int` to `int64_t` on the public `Network::cast` surface is backward-compatible because no caller in UtinniCore passes a value that needs more than 32 bits (checked: `network.h:39` is the only declaration; no managed binding calls it). [ASSUMED — grep would confirm]

**Harness (D-04 CR-02):** A new `utinni_test_networkCast` export that:
1. Creates a local `int64_t castDoubleNetworkId = 0;` and a local `pCast` function pointer pointing to a test stub that writes `(int64_t)0xDEADBEEFCAFEBABELL` through its OUT param.
2. Temporarily reseats `swg::network::cast` to the test stub (function pointer assignment — the pointer is module-scope in the `swg::network` namespace).
3. Calls `Network::cast(0x12345678)`.
4. Restores original `swg::network::cast`.
5. Returns the result.

The xUnit test asserts the returned value equals `(long)0xDEADBEEFCAFEBABEL` — if the OUT param is declared too narrow (4-byte), only the low 32 bits survive and the assertion fails. This would catch a revert of the CR-02 fix.

**Feasibility of function-pointer reseat:** [VERIFIED: codebase read]
`swg::network::cast` is declared as `pCast cast = (pCast)0xAA4900;` in the `swg::network` anonymous namespace in `network.cpp`. It is a non-const module-scope variable. Reseating it from a test export in `test_exports.cpp` requires either:
- (a) Moving the declaration to a header (exposes it beyond the anonymous namespace), or
- (b) Adding a helper function in `network.cpp`/`network.h` like `void swg::network::overrideCastForTest(pCast fn)` that the test export calls.

Option (b) is preferred (CON-N-02: the wrapper caller surface does not change; only a test-seam is added). The override function sets/restores the pointer.

### CR-03: `(id >> 32)` — UB on 32-bit `int`

**File:** `UtinniCore/swg/misc/network.cpp:70`

**Current state (verified):**
```cpp
int64_t Network::cast(int id)   // id is 32-bit
{
    swg::network::cast(&networkId, id, (id >> 32));  // shift by 32 on 32-bit int = UB
```

**Problem:** C++11 [expr.shift]/1: "The behavior is undefined" if the right operand is greater than or equal to the width of the promoted left operand. `sizeof(int)` is 4 on MSVC x86, so bit-width is 32. Shifting a 32-bit `int` by 32 is UB. On x86 hardware, `shr eax, 32` uses `cl & 0x1F = 0`, producing the original value (not zero), making the high half pass a copy of the original id — double bogus. [ASSUMED: x86 shift semantics from training; well-documented behavior]

**Fix (D-07 — unconditional):** The shift is dropped regardless of CR-02 disposition. As part of option (c) hybrid, `Network::cast` is widened to accept `int64_t id`, and the shift becomes well-defined:

```cpp
int64_t Network::cast(int64_t id)
{
    int64_t networkId = 0;
    swg::network::cast(&networkId,
                       (int)(id & 0xFFFFFFFFLL),
                       (int)((id >> 32) & 0xFFFFFFFFLL));  // well-defined: id is int64_t
    return networkId;
}
```

**Harness (D-04 CR-03):** The WR-01 test double harness described above also covers CR-03 implicitly — if the caller passes `id = 0x0000000100000000LL`, the new code passes `(int)0` for low and `(int)1` for high. The sentinel-based harness tests the full round-trip. A simpler static_assert can also verify the type:

```cpp
static_assert(sizeof(networkId) == 8, "CR-02 fix: networkId must be 8 bytes");
```

### WR-09: `CoInitializeEx` — no paired `CoUninitialize`

**File:** `UtinniCore/utinni.cpp:128`

**Current state (verified by direct read):**
```cpp
// utinni.cpp:128
CoInitializeEx(nullptr, COINIT_APARTMENTTHREADED);
// utinni_init then returns at :134; no CoUninitialize anywhere in utinni.cpp or detatch()
```

**COM consumer audit — result:** [VERIFIED: codebase grep]

Searched all of `UtinniCore/` for:
- `CoCreateInstance` — 0 hits
- `CoTaskMemAlloc` — 0 hits
- `IUnknown::QueryInterface` (native COM idiom) — 0 hits (only `ICLRMetaHost`, `ICLRRuntimeInfo`, `ICLRRuntimeHost` in `clr.cpp`, which are COM-like but activated via `CLRCreateInstance` not `CoCreateInstance`)
- `CoInitialize` / `CoUninitialize` — 1 hit (`utinni.cpp:128` — the call being audited)

**CLR Host apartment analysis:** `clr.cpp` uses `CLRCreateInstance(CLSID_CLRMetaHost, IID_ICLRMetaHost, ...)` (line 47) which is the metahost activation API. This does **not** use the COM apartment model — it is the "pure CLR bootstrap" path that bypasses the COM marshalling layer. Per MSDN documentation on `ICLRRuntimeHost`, it is free-threaded and does not require `CoInitializeEx` before calling it. [ASSUMED: training knowledge on CLR host threading model — consistent with CONTEXT.md WR-09 analysis]

**Recommendation (confirmed DROP):** `CoInitializeEx(nullptr, COINIT_APARTMENTTHREADED)` at `utinni.cpp:128` has no consumer in `utinni_init`'s downstream call chain. The CLR host does not require it. It should be removed entirely (cleanest fix) rather than paired with `CoUninitialize` (which would require scoping CoInitialize to a thread that survives for the needed duration — the utinni_init thread exits immediately after return 0 at :134).

**Threading note:** `utinni_init` is called on the launcher-spawned remote thread. That thread runs `createDetours()`, `createPatches()`, `pluginManager.loadPlugins()`, then `clr::load()` and returns. The apartment initialized on that thread is abandoned when the thread exits (the launcher's `WaitForSingleObject` then receives the exit code). An abandoned COM apartment is not a live resource from the process's perspective, but it is a resource-reference-count imbalance on the thread's TEB. Dropping the call removes the imbalance cleanly.

**Harness (D-04 WR-09):** The simplest verifiable harness is a static proof: after removing the `CoInitializeEx` call, a `grep` / CI compilation assertion confirms the function is gone. A runtime test could call a new test export `utinni_test_comApartmentCheck` that calls `CoGetApartmentType` and asserts `APTTYPE_CURRENT` returns `APTTYPEQUALIFIER_IMPLICIT_MTA` (i.e., no STA was initialized) — but this is overkill for a call deletion. The planner can choose between: (a) compile-time assertion (static_assert or just grep), or (b) a new test export + xUnit test that asserts no STA is initialized after a simulated `utinni_init` code-path. Option (a) is sufficient per D-04's intent.

### CR-04: `hPresentBlockedEvent` — TOCTOU lazy-init race

**File:** `UtinniCore/swg/graphics/directx9.cpp:40-53`

**Current state (verified by direct read):**
```cpp
// directx9.cpp:40 (file-scope, before namespace directX)
static HANDLE hPresentBlockedEvent = nullptr;

// directx9.cpp:45-53
extern "C" __declspec(dllexport) HANDLE __cdecl getPresentBlockedEvent()
{
    if (!hPresentBlockedEvent)  // <-- read
    {
        hPresentBlockedEvent = CreateEvent(nullptr, TRUE, FALSE, nullptr);  // <-- write
    }
    return hPresentBlockedEvent;
}
```

**The race:** Two distinct call paths can evaluate `!hPresentBlockedEvent` concurrently:
1. FormMain's `Lazy<EventWaitHandle>` initializer, which calls `GetPresentBlockedEvent()` P/Invoke on the managed UI thread on first access.
2. `hkPresent` at directx9.cpp:248 — the SWG render-thread detour — which reads `hPresentBlockedEvent` directly (not via `getPresentBlockedEvent()`).

If the render thread fires before `getPresentBlockedEvent()` has run, `hPresentBlockedEvent` is still `nullptr`. The render thread's `if (hPresentBlockedEvent) { SetEvent(...); }` guard at line 248 is safe (null-guard), but if the managed Lazy fires concurrently with `getPresentBlockedEvent()` being called by some other consumer, the TOCTOU between the null-check and the CreateEvent is unguarded.

The primary race window per the review: FormMain's Lazy invokes `getPresentBlockedEvent()` on the managed thread. If `hkPresent` has not yet fired, there is no second reader; but once the detour is armed, the render thread can call `SetEvent(hPresentBlockedEvent)` while `getPresentBlockedEvent()` is mid-CreateEvent on another thread. The assignment is not atomic on x86 when the compiler decides to reload from memory. [ASSUMED: C++ memory model reasoning — the assignment `hPresentBlockedEvent = CreateEvent(...)` is not guaranteed to be seen atomically by other threads without synchronization]

**D-08 — prefer eager init in `utinni_init`:**

`utinni_init` runs synchronously on the launcher remote thread and exits before:
- SWG's main loop starts (EP was patched with `0xEB 0xFE`; it is only restored after `WaitForSingleObject` at Launcher/main.cpp:232),
- Any detour fires (detours are created during `createDetours()` earlier in `utinni_init` but `hkPresent` cannot fire until SWG is executing and calls IDirect3DDevice9::Present, which requires the main loop to run).

Therefore creating `hPresentBlockedEvent` inside `utinni_init` before `createDetours()` returns is **completely safe** — it is a single-threaded operation with no concurrent reader. No `InterlockedCompareExchangePointer` needed. [VERIFIED: codebase read — utinni_init sequence at utinni.cpp:102-134]

**Proposed fix:**

```cpp
// utinni.cpp — inside utinni_init, before createDetours()
// Eagerly create the present-blocked event so hkPresent always finds a valid HANDLE.
// CON-N-01: this is NOT a Detour::Create call; it is additive event plumbing.
// CON-H-01: this runs in utinni_init (launcher remote thread), NOT DllMain.
hPresentBlockedEvent = CreateEvent(nullptr, TRUE, FALSE, nullptr);
```

This requires `hPresentBlockedEvent` to be declared with external linkage visible from `utinni.cpp`. Currently it is `static` at file scope in `directx9.cpp`. Options:
- (a) Declare it `extern HANDLE hPresentBlockedEvent;` in `directx9.h` and define it (without `static`) in `directx9.cpp`. `utinni.cpp` includes `directx9.h` and calls `CreateEvent` before the detour table is built.
- (b) Add a `directX::initPresentBlockedEvent()` function in `directx9.cpp` that `utinni_init` calls.

Option (b) is cleaner (keeps the symbol scoped to `directX::`) and aligns with CON-N-01 (no export, no new Detour). [ASSUMED: design preference consistent with existing pattern where `directX::cleanup()` is called from `detatch()` — same "init/cleanup called from utinni.cpp" pattern]

**getPresentBlockedEvent() post-fix:** After eager init, `getPresentBlockedEvent()` becomes a simple reader:
```cpp
extern "C" __declspec(dllexport) HANDLE __cdecl getPresentBlockedEvent()
{
    return hPresentBlockedEvent;  // always non-null after utinni_init
}
```

**Harness (D-04 CR-04):** Cannot reproduce the TOCTOU race from a unit test. But eager-init eliminates the lazy path entirely. The regression test asserts:
1. A new test export `utinni_test_getPresentBlockedEvent` returns a non-null HANDLE (would return null if someone re-introduced the lazy path and the test ran before the Lazy fired).
2. Optional: 1000-call loop from background threads all get the same HANDLE value (no double-create).

### WR-03: `depthTexture` — lazy allocation from render thread without synchronization

**File:** `UtinniCore/swg/graphics/directx9.cpp:254-263`

**Current state (verified by direct read):**
```cpp
// directx9.cpp:254-256 — inside hkPresent (render thread)
if (depthTexture == nullptr)
{
    depthTexture = new DepthTexture();

```

**DepthTexture constructor audit:** [VERIFIED: codebase read of depth_texture.cpp:44-58]

```cpp
DepthTexture::DepthTexture()
    : pTextureDepth(nullptr), m_isNVAPI(false), m_isSupported(false), pRegisteredDSS(nullptr), stage(5)
{
    if (NvAPI_Initialize() == NVAPI_OK)
```

Therefore `DepthTexture` **can be constructed before the D3D9 device is live** — its ctor only probes the GPU driver via NVAPI, which is available from any thread and any initialization state.

Move `new DepthTexture()` into `directX::initDepthTexture()` called from `utinni_init` before `createDetours()`, or at least before `utinni_init` returns. Same pattern as CR-04's eager init of `hPresentBlockedEvent`.

If the render thread is mid-frame when detach fires, this is a UAF. The fix per CONTEXT.md D-04 WR-03 is to **document the threading contract** (cleanup must run after render thread is quiesced) in a comment matching the C-10 idempotence comment style. The eager-init does not resolve this secondary concern; both the fix AND the comment are needed.

**Note:** `DepthTexture::createTexture()` (called at directx9.cpp:261) DOES require a live D3D9 device — it creates D3D9 textures. Eager construction of the `DepthTexture` object is safe; the `createTexture` call at line 259-263 must still remain inside `hkPresent` where `pDevice` is available. This is fine because the `hkPresent` code path already checks `depthTexture->getTextureDepth() == nullptr` before calling `createTexture`. [VERIFIED: codebase read]

**Harness (D-04 WR-03):**
- A test export `utinni_test_getDepthTexturePtr` that returns `(uintptr_t)directX::getDepthTexture()`.
- xUnit test asserts the returned value is non-zero (depthTexture was created before hkPresent fired — would be zero under lazy-init if run before first render frame).

### WR-01: `utinni_test_networkCast` — tautological sentinel stub

**File:** `UtinniCore/test_exports.cpp:104-112`, `UtinniCoreDotNet.Tests/NetworkCastTests.cs:46-61`

**Current state (verified by direct read):**

```cpp
    (void)id;
    return (int64_t)0xDEADBEEFLL;  // hardcoded; never calls Network::cast
```

The xUnit test asserts `result == 0xDEADBEEF`. This passes even if `network.cpp` is fully reverted. [VERIFIED: codebase read]

**Real harness plan (D-09 — function-pointer reseat):**

Step 1: Add a test-seam to `network.cpp`/`network.h`:

```cpp
    void setCastForTest(pCast fn);    // set a test double
```

Step 2: Rewrite `utinni_test_networkCast` in `test_exports.cpp`:
```cpp
// Test double: writes a 64-bit sentinel through the OUT param
static int64_t __thiscall testCastDouble(int64_t* networkId, int low, int high)
{
    // Write a known 64-bit sentinel (upper half distinguishes from 32-bit)
    *networkId = (int64_t)0xDEADBEEFCAFEBABELL;
    return 0; // return value is unreliable per CONCERNS.md TD-03; not tested
}

extern "C" __declspec(dllexport) int64_t __cdecl utinni_test_networkCast(int id)
{
    swg::network::setCastForTest((swg::network::pCast)testCastDouble);
    int64_t result = utinni::Network::cast((int64_t)id);
    swg::network::resetCast();
    return result;
}
```

The xUnit test asserts `result == (long)0xDEADBEEFCAFEBABEL`. If the CR-02 fix were reverted (OUT param back to `swgptr*` / 4 bytes), the test double would write 8 bytes through a 4-byte slot — either corrupting the stack (causing a crash the test catches) or the low 32 bits would not match the sentinel's high-half pattern.

**Calling convention note:** The test double must match the `__thiscall` ABI. On MSVC x86, `__thiscall` passes `this` in ECX; `int64_t*` is passed as the first explicit parameter (after ECX-pushed `this`). Since our test double is a static free function, we need to declare it `__thiscall` or use a `__cdecl` wrapper that mimics the calling convention. On x86 MSVC, `__thiscall` for non-member functions is permitted via an explicit calling convention declaration. [ASSUMED: MSVC x86 ABI knowledge]

Simpler alternative: keep the test double as `__cdecl` and use a lambda/adapter. In practice, since `pCast = int64_t(__thiscall*)(int64_t*, int, int)`, the function pointer type enforces the calling convention and MSVC will emit the correct calling convention for any function pointer assignment. The test double declared `int64_t __thiscall testCastDouble(int64_t*, int, int)` is the correct shape. [ASSUMED]

### WR-02: `utinni_test_freeConfigBuffer` — no-op stub

**File:** `UtinniCore/test_exports.cpp:86-94`, `UtinniCoreDotNet.Tests/ConfigBufferFreeTests.cs:47-72`

**Current state (verified by direct read):**

**Cross-CRT fixture plan (D-09):**

The C-02 fix removes a `delete[]` on a SWG-allocated buffer. The real risk is: if `delete[]` were re-added, it would call the UtinniCore CRT's heap free on a pointer allocated by SWG's CRT — a cross-heap free that corrupts the heap or crashes with `_ASSERTE(_BLOCK_TYPE_IS_VALID(pHead->nBlockUse))`.

To demonstrate this with a regression test, we need a buffer allocated by a DIFFERENT CRT than UtinniCore. This requires a fixture DLL with different CRT linkage.

### WR-05: `GetVtbl_WithoutD3d9Loaded_ReturnsNull` — negative-only test

**File:** `UtinniCoreDotNet.Tests/FindPatternHarnessTests.cs:109-116`

**Current state (verified):** The test asserts `Utinni_GetVtbl() == 0` when `d3d9.dll` is not loaded. This tests the null-guard fix (C-11) but not the positive path (pattern actually found). [VERIFIED: codebase read]

**WR-05 affirmative test investigation:**

The C-11 fix makes `getVtbl()` scan for a pattern `"\xC7\x06\x00\x00\x00\x00\x89\x86\x00\x00\x00\x00\x89\x86"` with mask `"xx????xx????xx"` inside the `d3d9.dll` module (directx9.cpp:336-337).

**Key question:** Is this pattern present in the static surface of `d3d9.dll` (i.e., in the file's code section), or is it only present at a runtime-initialized vtable that requires a live D3D9 device to populate?

**Analysis:** [ASSUMED: DirectX9 vtable pattern reasoning from training]

The pattern `\xC7\x06\x00\x00\x00\x00\x89\x86...` is a `mov [esi+0], imm32; mov [esi+offset], ...` sequence. This is characteristic of a constructor body that initializes a vtable pointer in a COM object. In D3D9's implementation, the vtable pointer for `IDirect3DDevice9` is stored in the COM object's first 4 bytes. The constructor code in `d3d9.dll` that initializes that vtable pointer is **static code in d3d9.dll** — it does not require a device to be created; it is bytecode that exists in the DLL's `.text` section regardless of runtime state.

**Conclusion:** `d3d9.dll` loaded via `LoadLibrary` in the test process WILL have the pattern in its code section **without creating a device**. The pattern scan `findPattern((swgptr)hD3d9, 0x128000, ...)` walks d3d9.dll's mapped memory looking for this bytecode sequence.

**Verification:** `d3d9.dll` (SysWOW64, x86) exists on the CI machine (`windows-2022`) at `C:\Windows\SysWOW64\d3d9.dll`. The test process is `x86` (net472, PlatformTarget=x86), so it loads the SysWOW64 variant. [VERIFIED: environment check showed SysWOW64\d3d9.dll is present at 1535160 bytes]

**Proposed test:**
```csharp
[Fact]
public void GetVtbl_WithD3d9Loaded_ReturnsNonZero()
{
    // LoadLibrary to ensure d3d9.dll is in the test process.
    // The test runner may or may not have it loaded already.
    IntPtr hD3d9 = NativeMethods.LoadLibrary("d3d9.dll");
    try
    {
        Assert.NotEqual(IntPtr.Zero, hD3d9); // d3d9.dll must be loadable on Windows
        UIntPtr result = NativeBridge.Utinni_GetVtbl();
        Assert.NotEqual(UIntPtr.Zero, result);
    }
    finally
    {
        if (hD3d9 != IntPtr.Zero)
            NativeMethods.FreeLibrary(hD3d9);
    }
}
```

This requires adding a `[DllImport("kernel32.dll")] IntPtr LoadLibrary(string)` and `FreeLibrary` to the test's `NativeBridge` class. Both are BCL-style P/Invokes (no new dependencies).

**Risk:** If the pattern is NOT present in the current Windows 10/11 d3d9.dll at the expected offset 0x128000, the test will return zero and fail. This would indicate the pattern needs updating in `getVtbl()`. Given that CI runs `windows-2022`, the pattern could differ from the SWG-era DXSDK June 2010 d3d9.dll. [ASSUMED: pattern compatibility risk]

**Fallback:** If the affirmative test cannot pass on the Windows Server 2022 CI image's d3d9.dll, document it as `[Fact(Skip = "WR-05: pattern is SWG-era specific; affirmative test requires SWG d3d9.dll — Tier-4")]`. The planner should attempt the test; if CI fails on the pattern, it degrades gracefully to documentation.

## Common Pitfalls

### Pitfall 1: Widening `Network::cast` parameter breaks existing callers

**What goes wrong:** Changing `int64_t Network::cast(int id)` to `int64_t Network::cast(int64_t id)` may cause implicit-narrowing warnings at call sites that pass `int` or `swgptr`.
**Why it happens:** C++ widening is implicit, but callers that were passing plain `int` will now be passing `int64_t` — no error, just a change in what value is passed to `swg::network::cast`'s low/high split.
**How to avoid:** After the change, `grep` for all callers of `Network::cast` in UtinniCore + UtinniPlugins (but D-10 says no cross-repo work; UtinniPlugins is untouched). In UtinniCore, `network.h` declares it; verify all callers are in the same compilation unit or include the header — they will pick up the widened signature automatically.
**Warning signs:** MSVC C4244 warning (narrowing from int64_t to int) if a caller tries to use the return value in a narrowing context.

### Pitfall 2: DepthTexture null dereference if depthTexture is created before D3D device

**What goes wrong:** `directx9.cpp:259` calls `depthTexture->getTextureDepth()` — if `depthTexture` is non-null but `getTextureDepth()` returns null (texture not yet created), the code falls into `createTexture(pDevice, ...)`. This is correct — the eager-init just pre-constructs the object; `createTexture` still fires on the first render frame. No bug.
**Why it could be perceived as a problem:** Someone sees `depthTexture != nullptr` on entry to `hkPresent` and thinks the first-frame `createTexture` branch is unreachable.
**How to avoid:** Add a comment: `// depthTexture is pre-constructed in utinni_init (ctor is D3D9-free); createTexture fires on first render frame when pDevice is available.`

### Pitfall 3: `__thiscall` test double calling convention mismatch

**What goes wrong:** `pCast` is `int64_t(__thiscall*)(int64_t*, int, int)`. A test double declared as `__cdecl` will be called with `__thiscall` ABI — ECX is expected to carry `this` (the pThis object pointer) but for a static function the callee does not receive it in ECX. The register mismatch causes undefined behavior or a crash.
**Why it happens:** MSVC treats `__thiscall` free-function declarations as `__stdcall` with ECX ignored — but only if explicitly declared. If the test double is mismatched it silently reads garbage in ECX.
**How to avoid:** Declare the test double as exactly `int64_t __thiscall testCastDouble(int64_t* networkId, int low, int high)` — MSVC accepts `__thiscall` on non-member functions as of C++17.

### Pitfall 4: `d3d9.dll` pattern not found on Windows Server 2022

**What goes wrong:** The WR-05 affirmative test calls `Utinni_GetVtbl()` after loading `d3d9.dll`. If the vtable init pattern `\xC7\x06\x00\x00...` is not present in `Windows\SysWOW64\d3d9.dll` on the CI image, `getVtbl()` returns null and the affirmative assertion fails.
**Why it happens:** The pattern is tied to the SWG-era DirectX SDK's d3d9.dll. Modern Windows ships a different d3d9.dll (DXGI wrapper) that may have different bytecode.
**How to avoid:** Run the affirmative test against a CI image first. If it fails, the test should `Skip` with a clear message rather than be deleted entirely. The null-path test (existing) remains valid and sufficient as a regression guard for C-11.

### Pitfall 5: Cross-CRT fixture only has explicit RuntimeLibrary on RelWithDbgInfo

**What goes wrong:** UtinniCore Debug and Release configs do not have an explicit `<RuntimeLibrary>` tag. If the effective CRT linkage for Release is `/MT` (static), a fixture using `/MD` is genuinely cross-CRT. But if Release defaults to `/MD` due to platform properties sheets, both UtinniCore and the fixture would use `MSVCRT.dll` and the "cross-CRT" test would not catch a real cross-CRT bug.
**Why it happens:** MSVC property sheet inheritance can set RuntimeLibrary without an explicit tag in the vcxproj.
**How to avoid:** At plan execution, verify UtinniCore Release's effective RuntimeLibrary by checking `cl.exe /showIncludes` output or adding a `#pragma message(...)` that prints the CRT linkage. The fixture must use the OPPOSITE linkage to create a real cross-heap scenario.
