### Concern A — WR-02 Marshal.AllocHGlobal harness may be partial-proof
**Plan:** 02.1-03 Task 1 (WR-02 ConfigBufferFreeTests rewrite)

The current `Marshal.AllocHGlobal` approach allocates from `GetProcessHeap()`. UtinniCore's `Release|Win32` build has NO explicit `<RuntimeLibrary>` tag (verified by RESEARCH §4) — the effective CRT is `/MT` (static), but modern MSVC v142 routes `/MT` `new[]`/`delete[]` through `_malloc_base`/`_free_base` → `GetProcessHeap()`. If both heaps are the same process heap, calling `delete[]` on an `AllocHGlobal` pointer in Release won't actually crash — it'll free the OS-heap pointer correctly. That means the WR-02 test would NOT fail if `delete[]` were re-introduced in `hkLoadOverrideConfig`, which is exactly the tautology we are trying to eliminate.

**Required executor action during Plan 02.1-03 Task 1:**
1. Before claiming WR-02 closed, verify the Release CRT heap behaviour. Cheapest probe: add a `#pragma message` or static_assert near `hkLoadOverrideConfig` OR run `cl.exe /verbose` against `config.cpp` once and capture which `_free_base` symbol the link resolves to.
2. If `/MT` Release uses `GetProcessHeap()` (likely): record this as a **partial-proof** test in the SUMMARY (it still exercises the no-op-export path and is better than the old stub) AND add a `// PARTIAL-PROOF: WR-02 cannot detect Release/MT cross-heap free without a separate /MD fixture` comment in the test file. Open a follow-up item to add a `Utinni.CrossCrtFreeFixture` vcxproj in Phase 6 STAB-03.
3. If `/MT` Release uses a private heap distinct from `GetProcessHeap()`: claim WR-02 fully closed.

This is the "verify CRT linkage" sub-step RESEARCH.md §A4 also flagged.

### Concern B — CR-04 / WR-03 tests as written are tautological (`x == 0 || x != 0`)
**Plan:** 02.1-02 Task 2 (mock-signaller test additions for `getPresentBlockedEvent` / `getDepthTexturePtr`)

The plan adds two `[Fact]` tests that exercise the test exports but only assert `Assert.True(result == UIntPtr.Zero || result != UIntPtr.Zero)` — a Boolean tautology. The plan acknowledges this in its own comments ("That is the contract being asserted here") because in a test process where `utinni_init` has not run, the exported HANDLEs are genuinely null and the export path is what gets exercised. **But this reproduces exactly the tautology pattern Phase 02.1 was opened to eliminate** (WR-01/WR-02 fixes the same class of issue in Plan 02.1-01/03).

The contract D-04 in CONTEXT.md says: "every fix lands with a regression test that would fail if the fix were reverted." These tests would not fail if `initPresentBlockedEvent()` were reverted to a lazy no-op (they'd still see null and still pass).

**Required executor action during Plan 02.1-02 Task 2:**
Add a `utinni_test_initPresentBlockedEvent()` test-only export in `UtinniCore/test_exports.cpp` that wraps `directX::initPresentBlockedEvent()` directly (not via `utinni_init` which needs the full SWG process). The xUnit test then:
1. Calls `Utinni_TestInitPresentBlockedEvent()` (now non-zero by contract)
2. Calls `Utinni_GetPresentBlockedEvent()` (now returns the same HANDLE)
3. Asserts both are equal AND non-zero

That would fail if `initPresentBlockedEvent()` were reverted to a lazy no-op (the first call would return zero) — meeting D-04. Same pattern for `depthTexture`: add `utinni_test_initDepthTexture()` and assert non-null.

The scaffolding the plan already provides (the basic exports + P/Invokes) is valuable and should stay; just add the init-export + non-null assertion on top. ~30 lines of additional code.

## Live-confirmed findings from Phase 02 manual UAT (2026-05-18)

### WR-03 manifests as exit-time D3D9 error dialog (CONFIRMED LIVE)

**Status:** Already in scope for Plan 02.1-02. The UAT just upgrades this from theoretical race to observed bug; no plan change needed, but executor should know the fix is load-bearing, not gold-plating.

**Live repro:**
1. Launch SWG via Utinni-injected Launcher.exe (Phase 02 C-01 flow).
2. Quit the SWG client.
3. On exit, SWG fires a "Direct3D could not be correctly initialized" error dialog.
4. **Negative control:** launch SWGEmu.exe directly (no Utinni). No dialog on exit.

**Root cause (as predicted by `02-REVIEW.md` WR-03):** `directX::cleanup()` deletes `depthTexture` on the `DLL_PROCESS_DETACH` thread. If the render thread is mid-frame at process exit, that's a use-after-free; SWG's D3D9 device-state validator catches the broken state on teardown and fires the canned dialog.

**Executor note for Plan 02.1-02:** Eager-init in `utinni_init` (the plan's primary CR-04/WR-03 strategy) fixes the STARTUP race but does NOT address the CLEANUP-side UAF. Two options for the cleanup side:
- (a) Document `directX::cleanup()`'s threading contract ("must run after render thread quiesced") and accept the exit-race as documented Tier-4 (won't crash production, just produces an exit-time dialog).
- (b) Skip the `delete depthTexture` in `directX::cleanup()` entirely — the process is exiting anyway, OS reclaims the memory. The `depthTexture = nullptr` reset is also moot on exit. Trade slight leak-on-exit for not-crashing-on-exit.

Option (b) is the conventional Win32 DllMain teardown pattern (don't do anything fancy on detach; let the OS clean up). The "leak" is bounded by process lifetime. Recommend (b) for cleanup, plus (a) as a doc comment.

### NEW finding from C-01 UAT — export-decoration harness gap (NOT in current 02.1 scope)

The C-01 live UAT caught a real bug that Plan 02-03's LoaderLockHarness missed:

**Bug:** `utinni_init` declared `extern "C" __declspec(dllexport) DWORD WINAPI utinni_init(LPVOID)` exports as `_utinni_init@4` (decorated stdcall name) on x86. The Launcher's `GetProcAddress(localCore, "utinni_init")` requested the undecorated name and failed — the error message `[ERROR] utinni_init export not found in UtinniCore.dll` shipped to production unobserved by any automated harness.

**Why the harness missed it:** `Utinni.LoaderLockHarness.exe` only times `LoadLibraryA("UtinniCore.dll")`. It never resolves `utinni_init` via `GetProcAddress`. The decoration mismatch is invisible to it.

**Fix (already landed in commit `389fc83`):** `#pragma comment(linker, "/EXPORT:utinni_init=_utinni_init@4")` adds an undecorated alias next to the decorated name. Both names now resolve in UtinniCore.dll's export table to the same RVA.

**Recommended addition to Plan 02.1-03 (Harness uplift):** Add a fourth harness — `utinni_test_resolveExports` — that opens a handle to UtinniCore.dll and asserts every documented C-linkage export (`utinni_init`, `utinni_findPattern`, `utinni_getVtbl`, `utinni_test_*`, `getPresentBlockedEvent`, etc.) resolves via `GetProcAddress` by its undecorated name. Two new exports' worth of decoration mismatch would otherwise re-introduce a "harness passes, production fails" gap. Approximately 50 LOC.

**Scope decision:** the planner can either (a) extend Plan 02.1-03 to include this fourth harness during execution, or (b) carry it into Phase 02.2 / Phase 03. Recommend (a) — it's small, lives in the same files as the existing harness work (`test_exports.cpp` + a new `ExportResolutionTests.cs`), and closes the recursion the plan-checker warned about (harnesses that don't exercise production code paths).
