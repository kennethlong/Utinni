## Summary

Phase 02.1 closes eight Phase-02 findings (CR-02, CR-03, CR-04, WR-01, WR-02, WR-03, WR-05, WR-09) and adds a new `utinni_test_resolveExports` harness. The core correctness fixes are sound: the 8-byte OUT param widening (CR-02), the `int64_t` shift fix (CR-03), and the eager-init ordering in `utinni_init` (CR-04/WR-03) are all implemented correctly. CoInitializeEx removal (WR-09) and the `cleanup()` delete-skip with a thorough comment (WR-03) are correct. No new Critical-tier defects were introduced by Phase 02.1's changes.

Four Warnings are raised. The most significant are: (1) `initPresentBlockedEvent()` leaks the previous Win32 HANDLE on repeated calls — the test export calls it unconditionally and could leak a kernel object on the second invocation within the same test run; (2) `initDepthTexture()` unconditionally `new`s a second `DepthTexture` on repeated calls, leaking the first allocation; (3) the naked-asm `testCastDoubleNaked` is declared `__cdecl` but cast to `__thiscall` — while the raw assembly manually implements the `__thiscall` ABI correctly, the `reinterpret_cast` is formally undefined behavior and could break under a future MSVC optimizer; (4) `GetVtbl_WithD3d9Loaded_ReturnsNonZero` loads d3d9.dll without verifying the test process is 32-bit, which will silently produce a zero result on a 64-bit test runner. Two Info items: one `getManger()` typo and one magic constant.

## Warnings

### WR-01: `initPresentBlockedEvent()` leaks a HANDLE on repeated calls

**File:** `UtinniCore/swg/graphics/directx9.cpp:59-63`

**Issue:** `directX::initPresentBlockedEvent()` unconditionally calls `CreateEvent` and assigns the result to `hPresentBlockedEvent` without checking whether it is already non-null. The test export `utinni_test_initPresentBlockedEvent()` (test_exports.cpp:225-229) calls this function directly. If the test is run twice in the same process — or if `utinni_init` runs and then the test export is also called — the first HANDLE is silently overwritten without `CloseHandle`, leaking a kernel object. Each leaked HANDLE occupies a slot in the process handle table. In test harnesses xUnit reuses the process across test classes, so this is a realistic code path.

**Fix:**
```cpp
void directX::initPresentBlockedEvent()
{
    if (hPresentBlockedEvent != nullptr)
        return;  // already initialized; do not overwrite or leak
    hPresentBlockedEvent = CreateEvent(nullptr, TRUE, FALSE, nullptr);
}
```

### WR-02: `initDepthTexture()` leaks the previous allocation on repeated calls

**File:** `UtinniCore/swg/graphics/directx9.cpp:81-84`

**Issue:** `directX::initDepthTexture()` unconditionally `new`s a `DepthTexture` and assigns it to the global `depthTexture` without checking whether `depthTexture` is already non-null. If this function is called more than once (e.g., the test export `utinni_test_initDepthTexture` is invoked and production `utinni_init` later also calls `initDepthTexture`, or two test runs share the process), the first allocation is leaked. Unlike the HANDLE leak, a `DepthTexture` may hold NvAPI state, making the double-init semantically incorrect in addition to being a memory leak.

**Fix:**
```cpp
void directX::initDepthTexture()
{
    if (depthTexture != nullptr)
        return;  // already initialized; guard against double-init
    depthTexture = new DepthTexture();
}
```

### WR-03: `reinterpret_cast` from `__cdecl` function pointer to `__thiscall` function pointer is undefined behavior

**File:** `UtinniCore/test_exports.cpp:124, 179`

**Issue:** `testCastDoubleNaked` is declared `extern "C" __declspec(naked) int64_t __cdecl testCastDoubleNaked()` (line 124). At line 179 it is cast via `reinterpret_cast<pCast>(testCastDoubleNaked)` where `pCast` is `int64_t(__thiscall*)(int64_t*, int, int)`. The calling convention in the C++ type system does not match. MSVC currently tolerates this because `__declspec(naked)` suppresses all compiler-generated prologue/epilogue and the inline assembly manually implements the correct `__thiscall` ABI (ECX = first param, `ret 8` callee-clean). However, the `reinterpret_cast` between incompatible function pointer types is formally UB under the C++ standard. Future MSVC versions with stronger calling-convention enforcement could reject this cast or generate an indirect call stub with the wrong convention. Additionally, the `__cdecl` declaration causes the compiler to emit no frame setup at all — the inline asm `push ebp / mov ebp, esp` prologue is correct but the `mov esp, ebp / pop ebp` epilogue is redundant with `ret 8` on a naked function and does not harm correctness. The UB cast is the real concern.

**Fix:** Declare the function with no calling convention keyword and rely purely on the naked asm body. Because MSVC C3865 blocks `__thiscall` on non-member functions, the cleanest alternative is to keep `__declspec(naked)` but remove the `__cdecl` specifier from the declaration (naked functions on x86 default to the surrounding calling convention for the pointer type, not for code emission):

```cpp
// Remove __cdecl from the declaration; the naked body is self-contained.
// The cast to pCast is still a reinterpret_cast, but the mismatch in the
// type system is eliminated because no convention is declared.
extern "C" __declspec(naked) int64_t testCastDoubleNaked()
{
    __asm { ... }  // body unchanged
}
```

Alternatively, wrap the call site in a small `__declspec(naked)` thunk that truly is `__thiscall` so the cast is type-correct. If neither approach is acceptable, add a static_assert or a comment clearly marking this as a MSVC-specific deliberate deviation from the standard with a reference to the MSVC behavior documentation.

### WR-04: `GetVtbl_WithD3d9Loaded_ReturnsNonZero` test silently passes vacuously on a 64-bit test runner

**File:** `UtinniCoreDotNet.Tests/FindPatternHarnessTests.cs:132-165`

**Issue:** `getVtbl()` in `directx9.cpp` uses `memcpy(&vtbl, (void*)(((swgptr)pDevice) + 2), 4)` — it copies exactly **4 bytes** into a `swgptr*`, which is correct only on 32-bit builds (`swgptr` is presumably `uint32_t` / pointer-sized for x86). The test process is built as `AnyCPU` (default for .NET xUnit projects). On a 64-bit CI runner the test host is `dotnet.exe` (64-bit), which means `LoadLibraryA("d3d9.dll")` loads the **64-bit** `system32\d3d9.dll` into a 64-bit process. `UtinniCore.dll` is built as x86 (`Win32` platform in the vcxproj). A 64-bit process cannot load a 32-bit DLL; `LoadLibraryA` will succeed for the 64-bit d3d9.dll but `GetModuleHandle("d3d9.dll")` inside `UtinniCore.dll` (which runs in a 32-bit in-process context via COM activation or WOW64) will not see the 64-bit handle. If the test runner is the .NET 32-bit runner (`dotnet test --arch x86`), `SysWOW64\d3d9.dll` is loaded correctly. Without a platform constraint, this test either fails with `Assert.NotEqual(IntPtr.Zero, hD3d9)` on a 64-bit host (if WOW64 can't load UtinniCore.dll at all) or produces a confusing pass because `Utinni_GetVtbl()` returns 0 (d3d9.dll in the 64-bit host namespace is invisible to the 32-bit DLL) but the test checks for non-zero. The `Assert.NotEqual(IntPtr.Zero, hD3d9)` at line 154 would catch the first scenario; the second scenario (h non-zero but vtbl zero) would cause `Assert.NotEqual(UIntPtr.Zero, result)` to fail at line 158 — failing for the wrong reason with a confusing message. More critically: if the CI runner happens to be 32-bit, the test passes. If it is 64-bit, it may produce a misleading failure message that does not identify the architecture mismatch as the root cause.

**Fix:** Add `[PlatformSpecific(TestPlatforms.Windows)]` and ensure the test project's `<RuntimeIdentifier>` or the test invocation uses `--arch x86` to guarantee the 32-bit process context that matches UtinniCore.dll's build target. Alternatively add a `Skip` reason that explains the 32-bit requirement, matching the pattern described in the existing comment at lines 140-145:

```csharp
[Fact(Skip = "WR-05: requires 32-bit test runner (--arch x86) to match UtinniCore.dll (Win32 platform); " +
             "64-bit dotnet host cannot load SysWOW64\\d3d9.dll into the same address space as a 32-bit DLL.")]
public void GetVtbl_WithD3d9Loaded_ReturnsNonZero()
```

**File:** `UtinniCore/swg/misc/network.h:46`, `UtinniCore/swg/misc/network.cpp:58`

**Issue:** `Network::getManger()` is a long-standing API name misspelling of "getManager". As a `UTINNI_API`-exported function it appears in the CppSharp-generated bindings. Fixing it is a breaking change to any caller; the omission does not introduce a bug, but it is worth tracking as a rename target for a future API-cleanup phase.

**Fix:** Rename to `getManager()` in a dedicated API-cleanup phase, updating CppSharp-generated wrappers and any managed callers simultaneously.

### IN-02: Magic constant `0x1000000` in `isServerId` should be a named constant

**File:** `UtinniCore/swg/misc/network.h:54`

**Issue:** `if (id >= 0x1000000)` uses a bare magic number. The value is presumably the SWG server-side object ID threshold. A named constant or comment tying this to the SWG protocol spec would make future maintenance safer.

**Fix:**
```cpp
// SWG server-side object IDs start at 0x1000000 (per SWG protocol).
static constexpr int64_t kServerIdThreshold = 0x1000000;
static bool isServerId(int64_t id)
{
    return id >= kServerIdThreshold;
}
```
