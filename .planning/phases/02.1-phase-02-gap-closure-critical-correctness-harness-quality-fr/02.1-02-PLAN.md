<objective>
Close CR-04 and WR-03 from the Phase 02 code review: both are lazy-init TOCTOU races eliminated by eager initialization in `utinni_init`.

CR-04: `hPresentBlockedEvent` is created lazily in `getPresentBlockedEvent()` without synchronization. FormMain's `Lazy<EventWaitHandle>` invokes it on the UI thread; `hkPresent` reads the raw HANDLE on the render thread. Both observe null concurrently — two `CreateEvent` calls can race, leaking one HANDLE and leaving FormMain with a stale HANDLE. Fix: call `directX::initPresentBlockedEvent()` in `utinni_init` before `createDetours()`. The launcher-spawned thread runs `utinni_init` synchronously and `hkPresent` cannot fire until SWG's main loop is running (main loop is parked until `WaitForSingleObject` at Launcher/main.cpp:232 returns). No concurrency is possible at init time.

WR-03: `depthTexture` is allocated inside `hkPresent` (render thread) on first frame. `directX::cleanup()` calls `delete depthTexture` from the `DLL_PROCESS_DETACH` thread — a use-after-free if the render thread is mid-frame. Fix: call `directX::initDepthTexture()` in `utinni_init`. The `DepthTexture` ctor calls only `NvAPI_Initialize()` and sets boolean fields — it does NOT require a live D3D9 device (verified in RESEARCH §WR-03). Document the cleanup threading contract.

Pattern: `directX::initFoo()` called from `utinni_init` before `createDetours()` — identical to the C-09 `getPresentBlockedEvent` export landing zone in Plan 02-04. Add `initPresentBlockedEvent()` and `initDepthTexture()` to directx9.h and implement in directx9.cpp. `utinni.cpp` already includes `directx9.h` so the calls compose cleanly.

Per D-04, add test exports and xUnit assertions that would fail if the lazy path were re-introduced.

Purpose: Eliminate two lazy-init race windows by moving allocation to the single-threaded utinni_init start path.
Output: Updated directx9.cpp/h, utinni.cpp, test_exports.cpp; new test assertions; assessment.md updated.
