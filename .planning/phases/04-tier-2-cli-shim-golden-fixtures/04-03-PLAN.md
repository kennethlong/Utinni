From Research §"Format-Specific Knowledge §IFF chunk format" (cross-confirmed against EA-IFF-85 public spec):
- Chunk shape: 4 bytes TypeID (ASCII, left-padded with space if shorter — `CAT ` has a trailing space) + 4 bytes signed Length BE + Length bytes Data + optional 1 byte pad if Length is odd (Motorola 68000 word alignment, preserved in spec).
- Length field is a 32-bit BIG-ENDIAN SIGNED integer specifying byte size of the data NOT including the 8-byte header. Negative values are invalid.
- Container chunks: `FORM`, `LIST`, `CAT ` (with trailing space), `PROP`. Their payload begins with a 4-char sub-type ID, then a sequence of nested child chunks.
- Leaf chunks: every other 4-char TypeID. Data is opaque to the IFF reader; meaning is application-specific (SWG-specific examples include `INFO`, `DATA`, `BODY`, `NAME`, `DESC`).
- Endianness pitfall: TRE is little-endian, IFF is big-endian. Per Research §"Endianness pitfall" — DO NOT share BinaryReader subclass with TRE's parser. Use a dedicated `ReadInt32Be(BinaryReader)` static helper.

From Research §Security Domain (mitigation requirements):
- T-04-V5: every length field must be checked: `if (length < 0)` → IffParseException(NegativeLength); `if (chunk_end > file_end)` → IffParseException(ChunkLengthExceedsFile); `if (chunk_end > parent_end)` → IffParseException(NestedChunkOverflow).
- T-04-DoS: enforce `MaxChunkSize = 64 * 1024 * 1024` (64 MB) per the Security Domain pattern table — IFF lengths exceeding this throw IffParseException(ChunkLengthExceedsCap) before any allocation occurs.

From Code Examples §Example 2 (idiom only — implementer writes the canonical Utinni-flavoured implementation; do not copy verbatim):
- The recursive descent shape: `ReadChunk(BinaryReader br, long parentEnd)` — read TypeID, read big-endian Length, compute `chunkEnd = position + length`, bounds-check vs parentEnd, dispatch to ContainerChunk vs LeafChunk based on TypeID membership in `{ "FORM", "LIST", "CAT ", "PROP" }`, consume pad byte if length is odd.

<json_contract>
The `inspect-iff` JSON envelope follows D-10 (sorted keys, indented 2 spaces, UTF-8 no BOM, LF line endings, `schemaVersion: 1`) PLUS the dual tree+flat projection described below.

**Top-level shape** (after JsonOutput.EmitSuccess wraps the result):

```
{
  "command": "inspect-iff",
  "result": {
    "schemaVersion": 1,
    "source": "<absolute-path-or-fixture-path-mask>",
    "tree": { ...root chunk... },
    "flat": { "nodes": [...], "edges": [...] }
  }
}
```

**Tree projection (hierarchical):**

Each chunk node carries these keys (sorted alphabetically by the SortedKeyContractResolver from Plan 04-01):

- `id`: stable path through the chunk tree. Format: `<FOURCC>:<typeHint>/<ordinal>/<FOURCC>:<typeHint>/<ordinal>/...` where typeHint is the FORM/CAT/LIST/PROP sub-type tag for container chunks (or the leaf's TypeID re-used). Examples: `FORM:WSNP/0`, `FORM:WSNP/0/PROP:DATA/0`, `FORM:WSNP/0/FORM:OBJS/1`. Ordinals start at 0 within each parent. The root's id is `<root-typeId>:<root-subTypeId>/0`.
- `kind`: `"container"` or `"leaf"`.
- `lengthBytes`: integer, the declared payload length (excluding the 8-byte header and the alignment pad).
- `typeId`: 4-char string, preserving trailing spaces (`"CAT "` carries the trailing space).
- For containers: `subTypeId` (4-char string) + `children` (array of child nodes, recursively).
- For leaves: `dataBase64` (Base64-encoded payload bytes — Base64 is JSON-safe and round-trippable, vs hex-string which would double the size). Empty payload serialises as `""`.

**Flat projection (`flat.nodes` + `flat.edges`):**

The flat view is the same data, restructured for graph-visualisation consumers:

- `flat.nodes`: array of `{ id, kind, lengthBytes, name, parentId, typeId }` objects, in preorder traversal order. `name` is the human-readable label (`<typeId>` for leaves, `<typeId> <subTypeId>` for containers). `parentId` is null for the root node and the parent's `id` for all others.
- `flat.edges`: array of `{ from: parentId, to: childId }` objects, one per parent-child relationship.

**React Flow portability note (verbatim — embed in the parser's xmldoc summary AND in the CLI command's class comment, and include in this `<json_contract>` block per CONTEXT.md §plan_03_scope):**

"Both `tree` and `flat` views derive from the same parser pass — they are alternative projections of one data structure, not two parses. The flat view is included so future React Flow tooling can lift this output without re-shaping it. Do NOT drop the flat view in 'cleanup' refactors — it is a stable part of the schemaVersion: 1 contract."

The future React Flow consumer is expected to call `useNodesState(json.result.flat.nodes)` and `useEdgesState(json.result.flat.edges)` directly. Maintaining stable `id` strings across both projections is what makes that lift possible — do not let an executor or future refactor "simplify" by emitting only one view.
</json_contract>
