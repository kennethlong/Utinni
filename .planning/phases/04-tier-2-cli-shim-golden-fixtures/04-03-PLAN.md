From Research §"Format-Specific Knowledge §IFF chunk format" (cross-confirmed against EA-IFF-85 public spec):
- Chunk shape: 4 bytes TypeID (ASCII, left-padded with space if shorter — `CAT ` has a trailing space) + 4 bytes signed Length BE + Length bytes Data + optional 1 byte pad if Length is odd.
- Length field is a 32-bit BIG-ENDIAN SIGNED integer specifying byte size of the data NOT including the 8-byte header. Negative values are invalid.
- Container chunks per EA-IFF-85: `FORM`, `LIST`, `CAT ` (with trailing space). NOTE per REVIEWS MEDIUM-14: PROP IS NOT A CONTAINER — PROP is a LEAF chunk per EA-IFF-85 spec ("Property chunks are leaves whose payload is one or more 8-byte property records"). The original plan listed PROP as a container; this was incorrect.
- Container chunk payloads begin with a 4-char sub-type ID, then a sequence of nested child chunks.
- Leaf chunks: every other 4-char TypeID, INCLUDING PROP. Data is opaque to the IFF reader; meaning is application-specific (SWG-specific examples include `INFO`, `DATA`, `BODY`, `NAME`, `DESC`, `PROP`).
- Endianness pitfall: TRE is little-endian, IFF is big-endian. Use a dedicated `ReadInt32Be(BinaryReader)` static helper.
- Word-alignment: per spec, IFF requires word-alignment (offsets to chunk headers must be even). After an odd-length chunk's payload, ONE zero-byte pad MUST appear before the next chunk's header. REVIEWS MEDIUM-11 + iter-3 MED-3 STRICT: if an odd-length chunk reaches `parentEnd` (or stream.Length when parentEnd == stream.Length) without the pad byte, the parser throws IffParseException(Truncated).

From REVIEWS MEDIUM-11 (pad-byte STRICT decision) + iter-3 MED-3 (boundary is parentEnd):
- Chosen: STRICT. Missing pad byte at parent boundary → Truncated.
- Iter-3 MED-3: the relevant boundary is the parent's end, not file EOF. For the outermost FORM, parentEnd == stream.Length; for nested children, parentEnd is the parent FORM's payload end. Pad-byte consumption MUST check `position < parentEnd`. When `position == parentEnd` AND the child had odd length, throw Truncated.

<pitfalls>
**Pitfall A (REVIEWS MEDIUM-14 closed): PROP is a LEAF, not a container.**

EA-IFF-85 §"Property Chunks" defines PROP as containing one or more property records `(propertyId:int4, length:int4, value:byte[length])`. While the records are STRUCTURED, the chunk itself does NOT contain arbitrary nested IFF chunks — it is a leaf at the IFF chunk-graph level. Earlier plan revision incorrectly listed PROP in `ContainerTypeIds`; this is now `{ "FORM", "LIST", "CAT " }` only.

The `synthetic-secondary.iff` fixture is the explicit regression guard: it includes PROP children inside a `CAT ` container, and the goldens assert each PROP is parsed as `IffLeafChunk`.

Spec citation: EA-IFF-85 spec rev 1985-10-15 §"Standard Chunks for Property Definition (PROP)" treats PROP as a leaf carrying property records, distinct from containers (FORM/LIST/CAT).

**Pitfall B (REVIEWS MEDIUM-11 + iter-3 MED-3 closed): STRICT missing-pad-byte behavior at PARENT BOUNDARY.**

Per EA-IFF-85: odd-length chunks must be followed by a single 0x00 pad byte before the next chunk. The parser ENFORCES this AT PARENT BOUNDARIES (iter-3 MED-3 — NOT just EOF): if an odd-length chunk reaches `parentEnd` without the pad byte present, IffReader throws `IffParseException(Truncated)`. For the outermost FORM, parentEnd == stream.Length (the original REVIEWS MEDIUM-11 case); for nested children, parentEnd is the parent FORM's payload end. The `malformed-missing-padbyte.iff` fixture + Tier-1 tests `Read_OddLengthLeafAtEofMissingPad_ThrowsTruncated` (EOF case) AND `Read_OddLengthLeafAtParentEnd_NoPad_ThrowsTruncated` (nested parent case) BOTH enforce this contract.

Rationale: lenient behavior (skip the pad check at parent boundaries) silently accepts malformed/corrupt files; worse, a pad byte that belongs to the PARENT's slack space could be consumed and hide malformed nested data. Phase 4's purpose is regression-protection — silent acceptance defeats the purpose.

**Pitfall C (REVIEWS MEDIUM-12 closed): No real-sample.iff in Phase 4.**

The original plan revision had a `real-sample.iff` fixture sourced from a clean SWG install. This is REMOVED — Phase 4 ships ONLY synthesized fixtures to preserve D-01 clean-room posture without licensing review overhead. The cross-validation use case is served by `synthetic-secondary.iff` (structurally distinct from the primary synthetic-nested fixture).

If a future phase needs real-sample coverage (Phase 7+ TRE Browser, Phase 8 IFF Editor), it lands via a separate commit with explicit licensing review and a stronger justification than "cross-validation" — e.g., a specific real-world edge case the synthesized fixtures cannot construct.

**Pitfall D (plan-checker iter-2 WARNING-8 — fixture-cap documentation).** Per CONTEXT.md D-03 the absolute fixture cap is 256KB; this plan enforces a tighter operational 128KB cap (per CONTEXT.md D-08's observed "small (<128KB each)" target) because synthesized fixtures comfortably fit there. The 128KB gate (`131072` bytes in PowerShell `Where-Object { $_.Length -gt 131072 }` verify-gates) is a self-imposed regression guard, NOT a contradiction of D-03's ceiling. If a future revision needs to ship a single sample between 128KB and 256KB (still legal per D-03), the verify-gate threshold for that fixture is bumped explicitly in the plan diff — never silently.

**Pitfall E (iter-3 HIGH-2 closed): Parser check order is locked; fixtures designed to land in expected error buckets.**

The parser bounds-check order is fixed at NegativeLength → ChunkLengthExceedsCap (64MB) → ChunkLengthExceedsFile → NestedChunkOverflow. Fixtures are designed to land in the expected error bucket given this order:
- `malformed-chunk-overflow.iff`: declared length `0x00100000` (1 MB, under cap) in a ~30-byte file → ChunkLengthExceedsFile (cap check passes; file-bound check fires).
- `malformed-truncated.iff`: outer FORM length 200 in a ~210-byte file with inner sub-chunk claiming 180 bytes but file truncates at offset 100 → recursive descent into inner chunk reads past EOF, throws Truncated (outer cap + outer file-bound checks pass; inner descent then fails).

If a future fixture is added with a declared length that trips a different check, the fixture name + golden `error.kind` must match that check's bucket — never silently widen the parser to accept other kinds.
