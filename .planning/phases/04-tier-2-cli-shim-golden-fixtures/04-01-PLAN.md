<json_contract>
<!-- The LOCKED Phase 4 JSON envelope shape. Per REVIEWS HIGH-6, every command's output (success or error) follows this exact envelope at the ROOT level. -->

**Success envelope:**
```
{
  "command": "<verb-name>",
  "result": { ... command-specific payload ... },
  "schemaVersion": 1
}
```

**Error envelope:**
```
{
  "command": "<verb-name>",
  "error": {
    "kind": "<error-kind-slug>",
    "message": "<human-readable detail>"
  },
  "schemaVersion": 1
}
```

**Locked invariants (apply to all four plans 04-01 through 04-04):**
- `schemaVersion` is at the ENVELOPE ROOT — NEVER nested inside `result` or `error`.
- `command` is at the ENVELOPE ROOT — names the verb that produced the envelope.
- `result` and `error` are MUTUALLY EXCLUSIVE — exactly one MUST appear in each envelope; never both.
- Top-level keys after sorted-key serialization: success = `command, result, schemaVersion`; error = `command, error, schemaVersion`.
- The `error` sub-object has at minimum `kind` (machine-readable slug) and `message` (human-readable string). Commands MAY add structured context (e.g. offset, expected-vs-actual), but `kind` and `message` are the locked invariants.
- `schemaVersion: 1` is the only currently-defined version; future bumps go to 2 and break the contract intentionally.

**Tier-1 envelope test required (Task 1.2 must include):** A dedicated `JsonOutput_Envelope_HasTopLevelSchemaVersionAndCommand` test asserting both `schemaVersion` and `command` parse as top-level JToken keys and that `result`/`error` contains neither.
</json_contract>
