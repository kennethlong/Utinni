From Research §"Format-Specific Knowledge §TRE container format" (cross-confirmed against `swg-client-v2/TreeFile.cpp` format-reference-read):
- Magic: 4 ASCII bytes `EERT` at offset 0 (the string "TREE" stored as little-endian 32-bit = `0x45455254`).
- Version: 4 ASCII bytes at offset 4. Phase 4 supports `0005` + `0006`. Any other value → TreParseException(UnsupportedVersion).
- Byte order: little-endian for all 4-byte integers in the header and per-record info.
- Header (28 bytes post-version): ResourceCount(int32), InfoOffset(int32), InfoCompression(int32), InfoCompressedSize(int32), NameCompression(int32), NameCompressedSize(int32), NameSize(int32).
- Per-record TreInfo struct (24 bytes): DataSize(int32), DataOffset(int32), DataCompression(int32), DataCompressedSize(int32), Checksum(int32), NameOffset(int32). InfoSize derived as ResourceCount * 24.
- Names block: concatenated null-terminated ASCII filenames at InfoOffset + InfoSize (if InfoCompression == 0) or after inflated InfoBlock if InfoCompression != 0.
- Compression: zlib/deflate when *Compression == 1. Phase 4 uses `System.IO.Compression.DeflateStream` for inflation; raw deflate (no zlib 2-byte header) is the swg-client-v2 convention.
- Lookup semantics: case-insensitive filename match (out of scope for Phase 4 - we just emit the names; consumers do their own lookup).

From Research §Security Domain (mitigation requirements):
- T-04-V5/DoS: every `length` / `*Size` field must be checked: `if (claimedSize < 0 || claimedSize > maxBound)` → TreParseException. maxBound = 256 MB per record, 256 MB per inflated block.
- T-04-DoS: DeflateStream output capped at 256 MB via a wrapper stream that throws if the cumulative read exceeds the cap.
