<objective>
Ship Phase 9's typed DTII format primitives — Layer 1 of the editor stack. This plan introduces the
**framework-side** `UtinniCoreDotNet/Formats/Datatable/` namespace (CF-01) carrying ten pure-managed
files: the typed `DataTableDocument.FromIff` reader, the `MutableDataTableDocument` mutable model
with the CF-04 hybrid-DOM original-byte preservation at per-cell granularity, the
`DataTableColumnType` type-spec parser + `MangleValue` port from SOE source, the `DataTableHashCrc`
port of `Crc::normalizeAndCalculate`, and the `DataTableWriter` that composes Phase 8's existing
`IffWriter.Write` on a freshly-built `FORM DTII { FORM <ver> { COLS, TYPE, ROWS } }` tree.

Five xUnit test files cover the parser, MangleValue, CRC parity, document FromIff for V0+V1, writer
round-trip byte-exact (no edits, canonical fixtures), and the structural SC4 invariant
(`EditCellValue → Undo → bytes EXACTLY equal loaded bytes`) via the new CaptureState/RestoreState
revert path. All test files land under `UtinniCoreDotNet.Tests/FormatsTests/Datatable/` which is
SDK-style auto-glob — no test-csproj edit needed.

**Byte-exact scope (iter-2 item 4 — codex HIGH):** the SC4 byte-exact claims here are bounded — see
the `assumes` byte-exact-scope entry. Whole-file byte-exactness is asserted for the synthetic
CANONICAL fixtures (which are valid-by-construction through the framework primitives) and the
edit→undo invariant is asserted at per-cell-slice granularity. Arbitrary hand-authored chunk
layouts / unusual chunk order / type-spec spelling variants are explicitly OUT of the guaranteed
scope unless the hybrid DOM provably preserved those whole original chunks.

**Why this decomposition:** Format primitives are the foundation every other Phase 9 plan composes
on. Splitting them into their own wave-1 plan keeps the context cost tractable (10 framework files +
5 test files in one plan stays under the ~50% target because the patterns are mechanical ports of
Phase 8 + SOE source), allows Plan 09-02 (CLI round-trip gate) to start in parallel as soon as the
public API is sketched, and surfaces all the C++→C# port risk (CRC algorithm, type-spec grammar)
at the earliest possible point.
